# MizTrace 项目评审 + 日记模块 / 技能模块设计

> 历史设计稿，部分现状描述已过时。2026-11-27 起以 [开发进度](./开发进度.md) 和实际代码为准：原项目已有 CI 和 journals 持久化，本轮新增了日记库、Markdown 编辑与桌面分发工程。

> 2026-09-30 评审。基于 commit 现状：`npm test` 198/198 全绿，零依赖，Node ≥22.13。

## 一、现状评估：哪些地方已经很好

- **架构干净**：`collect → modules → journal → render` 一条直线，`src/ai/` 唯一出站、`src/server/` 唯一监听，边界有 CI grep 守着。
- **存储层有迁移机制**：`db.js` 的 MIGRATIONS 顺序迁移、幂等，加新表没有历史包袱。
- **安全模型完整**：随机 token、Host/Origin 校验、CSP 锁死、密钥熔断、家目录替换。
- **前端无构建 Vue 3**，组件按职责拆分（dayboard / drawer / modals / notes / setup），样式是统一的设计变量体系（`--paper/--ink/--c-*`）。

## 二、需要完善的地方（按优先级）

### P0 — 不加新模块就该补的

1. **前端没有「页面」概念**。现在只有一个 `view`（board/list）切换，整个应用是单屏。日记库、技能都是独立页面，继续往 `app.js`（已 503 行）里塞会失控。
   → 方案：加一层**极简 hash 导航**（`#/board`、`#/journal`、`#/skills`），顶栏改成 tab。不需要 vue-router，30 行以内搞定，保持零依赖。

2. **`VERSION` 两处写死**：`package.json` 是 `0.3.0-dev`，`src/server/index.js` 第 40 行又硬编码一份。发版时迟早改漏。
   → 方案：server 从 `package.json` 读（`import ... assert { type: 'json' }` 或启动时 `readFileSync`）。

3. **仓库里没有 CI 配置**。README 说「CI 用 grep 守着两条边界」，但 `.github/workflows/` 不存在，grep 脚本也不在仓库里。
   → 方案：补一个 workflow：跑 `npm test` + grep 检查「出站只在 src/ai」「http 只在 src/server」。

### P1 — 为日记/技能模块铺路的

4. **`journals` 表建了但基本没用上**。`saveJournal` 只把 md 写到 `cfg.out` 目录，表里的 `markdown/out_path` 没有回写，历史日记在网页里完全看不到——保存即「消失」。
   → 这是日记模块的数据基础，见第三节。

5. **`web/lib/md.js` 渲染能力太弱**。只认标题/列表/引用/粗体/行内代码/脚注。一旦要展示「任意 markdown 文件」，表格、代码块、图片、链接、删除线全都不支持。
   → 方案：在现有 81 行的基础上增量补： fenced code block、表格、链接（`[t](u)` 只渲染文本+title，不真的可点，守 CSP）、图片（只渲染本站 `/api/` 开头的）。不引第三方库，估计 +150 行。

6. **日记不可编辑**。现在 draft 只有「生成 / 复制 / 保存」，改一个字都要去外部编辑器。
   → 见第三节的编辑设计。

### P2 — 可以顺手的

7. **顶栏已经拥挤**：日期导航 5 个按钮 + 视图切换 + 重置 + 规则版 + 生成日记 + 语言 + 设置，一行 12 个控件。加新模块入口后必须重构导航（与第 1 条一起解决）。
8. **`src/server/index.js` 601 行**，API 表继续长。建议按域拆成 `server/api-day.js / api-journal.js / api-skills.js`，入口只做接线。不急，加技能模块时顺手拆。

## 三、日记模块设计（「攒」的第一步）

**目标**：在网页里能浏览所有历史日记、打开看 markdown 渲染效果、直接编辑并保存。

### 数据层

- 来源两个，合并成统一列表：
  - `cfg.out` 目录下的 `YYYY-MM-DD.md` 文件（用户可能用 Obsidian 也在写同一个目录）；
  - `day_state.draft_md`（生成了但还没保存的草稿）。
- `journals` 表启用起来：保存时回写 `markdown + out_path`，作为索引和全文搜索的基础（db 有 FTS5 可用，二期再做搜索）。

### API（挂进现有 api 表）

| 接口 | 作用 |
|---|---|
| `GET /api/journals` | 日记列表：日期、标题（第一行）、字数、来源（草稿/已落盘）、mtime |
| `GET /api/journals/file?date=` | 读某天的 md 原文（优先 out 目录文件，没有就给草稿） |
| `PUT /api/journals/file` | 保存编辑后的 md：写回 out 目录 + 更新 day_state.draft + 回写 journals 表 |

安全约束与现有模型一致：只允许读写 `cfg.out` 目录内的 `*.md`，文件名必须是 `YYYY-MM-DD.md`，路径 resolve 后校验前缀，防目录穿越。

### 前端

- 新 tab **「日记」**，三栏或两栏：
  - 左：月份日历 + 有日记的日期高亮（或倒序日期列表，先做列表，日历二期）；
  - 右：markdown 渲染预览，顶部工具条「编辑 / 预览」切换。
- 编辑形态：**源码 textarea + 预览切换**（不做法所见即所得——零依赖约束下成本太高，且你的日记是自己看的，源码编辑够直接）。保存时给「已保存到 xxx」的 toast，沿用现有交互语言。
- 从时间板那天的 draft 也能一键跳进日记页（`#/journal?date=2026-09-30`）。

## 四、技能模块设计（README 路线图里的「我的技能」）

**目标**：一键从全部日记里提取技能档案；技能可能成千上万种，但只展示日记里真正涉及的；点进技能能看到对应的日记内容。

### 关键决策：技能从哪来、怎么收敛到「只显示涉及的」

你说的「成千上万种但只显示涉及的」，实现上不维护一个巨型技能词表去匹配（匹配不准、维护不动），而是：

1. **模型自由提取**：把日记分批喂给模型，要求输出结构化 JSON：`[{ name, category, level, evidence: [{ date, quote }] }]`。模型只会产出日记里出现过的技能——天然满足「只显示涉及的」。
2. **归并去重**：模型分多批跑，同一技能可能反复出现（「Vue」「Vue3」「vue.js」）。入库时按规范化名称合并（小写、去版本号），合并不了的留给用户在页面上手动「合并这两项」（二期）。
3. **增量更新**：skills 表记录每项技能来自哪些日期。再点「生成」时只把**新日记**发给模型，结果合并进现有档案，不用每次全量重跑——日记攒到几百篇后这是成本生死线。

### 数据层（迁移 v6）

```sql
CREATE TABLE skills (
  id          TEXT PRIMARY KEY,      -- 规范化名称
  name        TEXT NOT NULL,          -- 展示名
  category    TEXT,                   -- 前端/后端/数据库/协作/语言…
  level       TEXT,                   -- 了解/用过/熟练/主导（模型判，用户可改）
  first_date  TEXT, last_date TEXT,   -- 首次/最近一次出现
  hit_count   INTEGER DEFAULT 0,      -- 涉及多少篇日记
  stale       INTEGER DEFAULT 0,      -- 90 天没碰 → 置灰
  updated_at  TEXT NOT NULL
);
CREATE TABLE skill_evidences (
  skill_id  TEXT NOT NULL,
  local_date TEXT NOT NULL,
  quote     TEXT,                     -- 模型摘的那段日记原文
  PRIMARY KEY (skill_id, local_date)
);
```

「半年没碰变灰」就是 `last_date` 距今天数，查询时算，不用定时任务。

### API

| 接口 | 作用 |
|---|---|
| `GET /api/skills` | 技能列表（按类别分组、按最近活跃排序，stale 标记） |
| `GET /api/skills/detail?id=` | 单项技能：统计 + 涉及日期列表 + 每个日期的那段 quote |
| `POST /api/skills/generate` | 一键生成/增量更新（走现有 `writeWithAI` 的 provider 通道，出站前同样过 redact + 确认弹窗） |
| `POST /api/skills/level` | 用户手动修正熟练度（模型判的不一定服人） |

没配模型时的降级：规则版提取——内置一个很小的技术关键词表（语言/框架/数据库几十个常见词）做命中统计，只出「名字 + 出现日期」，不出 level。和日记的「规则版」一个思路。

### 前端

- 新 tab **「技能」**：
  - 列表页：按类别分组的卡片墙。每张卡：技能名、level 徽标、「12 篇日记 · 最近 3 天前」。stale 的整卡变灰 + 「N 个月没碰了」。
  - 详情抽屉/页：复用现有 Drawer 的视觉——顶部技能名 + level，中间一条从 first_date 到现在的时间线，下面按日期列出涉及的日记摘录，点日期跳到 `#/journal?date=xxx` 看那篇全文。
- 「一键生成」沿用现有发送前确认弹窗（PreviewModal）：显示将发送的日记篇数、估算 token，确认才发。这条是项目的铁律，技能模块不破例。

## 五、前端美化方向

现有「纸面 + 墨迹」的风格骨架是好的，不推倒，做三件事：

1. **导航重构**（配合 P0-1）：顶栏左侧品牌 + tab（时间板 / 日记 / 技能），右侧只留语言 + 设置。日期导航收到「时间板」页内，不再全局占位。
2. **精致度打磨**：
   - 板子加载时的骨架屏（现在只有一行「正在采集」小字）；
   - 日记页用阅读排版：衬线标题已有，正文行宽 76ch 已有，再补「纸张」质感（暖白底 + 细装订线）；
   - tab 切换、抽屉开合补 150ms 过渡，和现有 pop/rise 动画语言一致。
3. **可选：暗色模式**。`color-scheme` 现在锁死 light，设计变量全是 CSS 变量，加一套 dark 变量成本很低。但这是一口独立的饭，建议排最后。

## 六、实施顺序建议

| 阶段 | 内容 | 理由 |
|---|---|---|
| 1 | hash 导航 + 顶栏重构 + VERSION 单源 + CI 补上 | 改动小，是后面一切的地基 |
| 2 | 日记模块：journals API + md.js 增强 + 日记页（浏览 + 编辑） | 技能模块的数据前提 |
| 3 | 技能模块：db v6 + 生成接口 + 技能页 | 最重的部分，地基稳了再做 |
| 4 | 美化打磨（骨架屏、过渡、暗色可选） | 功能定了再调视觉 |
