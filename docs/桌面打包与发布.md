# MizTrace 桌面打包与 GitHub 下载

更新日期：2026-11-28。桌面工程位于 `desktop/`，核心 CLI 和网页版本仍可独立运行。

## 用户下载后如何使用

- Windows x64：下载 `MizTrace-Windows-x64-Setup.exe`，运行安装程序，之后从开始菜单或快捷方式打开。
- Mac Apple Silicon：下载 `MizTrace-macOS-arm64.dmg`，打开后把应用拖入 Applications。
- Mac Intel：下载 `MizTrace-macOS-x64.dmg`，安装方式相同。
- Mac 同时提供 ZIP。两个架构分别构建；此版本不提供通用二进制。

安装包包含 Electron 窗口、应用代码和独立 Node 运行环境，用户无需安装 Node、npm 或 Python。Git 痕迹采集仍依赖用户电脑上的 Git；没有 Git 时可以使用本地日记和编辑器。

## 本地开发与打包

构建机需要可运行 `node:sqlite` 的 Node，建议 Node 24，以及 npm。先在仓库根目录执行：

```bash
npm run desktop:install
npm run desktop:dev
```

生成安装包并验证真实打包后的程序：

```bash
npm run desktop:make
node scripts/desktop-smoke.mjs
# Mac 正式发行还必须通过签名、公证票据和 Gatekeeper 检查：
# node scripts/verify-macos-release.mjs
node scripts/release-assets.mjs
```

安装包在 `desktop/out/release/`。`desktop/out/`、`.build/`、`node_modules/` 都不应上传到 Git 源码仓库。安装包通过 GitHub Release 附件分发。

Windows 安装器使用的资源工具不支持中文绝对路径，因此 `desktop/make.mjs` 会在独立临时目录生成安装器，再把成品复制回项目。若系统临时目录本身也包含中文，可设置 `MIZTRACE_BUILD_TEMP_DIR` 为一个可写的英文路径；无需移动项目源码。

复制构建产物时保留原始符号链接。macOS Framework 的相对链接不能被改写为构建临时目录的绝对路径，否则清理临时目录后 App 将因找不到 Electron Framework 而启动失败；CI 会在清理之后启动复制出来的真实 App 验证。

Windows 包在 Windows 上生成；macOS 包在对应架构的 Mac 上生成。不要从 Windows 指定 `--platform darwin` 来冒充已经验证的 macOS 安装包，因为内置 Node 也必须匹配操作系统和架构。

## 上传 GitHub 后的发布步骤

1. 将项目源码和 `desktop/package-lock.json` 推送到你的 GitHub 仓库。
2. 先在 Actions 中选择 **Desktop release → Run workflow**，验证三个平台构建。手动运行只生成 Actions artifacts，不自动公开发行版。
3. 正式发布前，同时修改根目录 `package.json`、`desktop/package.json` 的版本号，并运行 `npm install --prefix desktop --package-lock-only` 同步锁文件。当前源码版本为 `0.5.2`；下次发布使用新的版本号，例如 `0.5.3`，并在 `releases/v版本号.md` 中填写面向用户的更新内容。
4. 在 `main` 上提交这些文件后，推送代码，再创建并推送同名版本标签。以下以**已提交版本号 0.5.3** 为例；不要重复创建已存在的标签：

```bash
git push origin main
git tag v0.5.3
git push origin v0.5.3
```

5. 三个平台测试、打包和真实 App 启动检查通过后，工作流先建立草稿 Release，上传安装包、更新源和校验文件，再公开发布，避免用户检测到尚未上传完的版本。更新说明优先使用 `releases/v版本号.md`，发布日期使用 GitHub 的实际发布时间。

发布任务串行进行，按版本号比较已发布的正式版，只有不低于现有正式版的版本才标记为 Latest。补发旧版、预发布版不会替换 README 的最新下载入口；已公开的 Release 重跑时不覆盖其资产。当前许可证、第三方声明和授权说明也随 Release 上传。

**正常发布无需手动创建 Release 或上传安装包。** `git push` 代码只触发 CI，推送 `v*` 标签才触发自动发行。Tags 页只有 `Source code (zip/tar.gz)` 时，表示那里只有源码快照，不能当作安装包；到 Actions 的 **Desktop release** 查看对应标签的运行结果。任一平台失败都会阻止发布，即使 Windows 构建已成功。只有 `release` 任务成功后，Releases 页面才会出现全部安装包和更新文件。

`Re-run failed jobs` 会重跑原提交；如果已经修改构建代码，重跑旧任务不会包含修复。已公开发行的版本应使用新版本号修复；尚未发行的失败标签，只有在确认没有用户下载的发行资产后才考虑修正其指向。

带连字符的标签（例如 `v0.3.0-beta.1`）会生成 prerelease。GitHub 的 `releases/latest` 指向正式发行版，所以测试版请使用带标签的下载地址。

README 中的下载链接形式如下，把 `OWNER/REPO` 换成你实际发布的仓库：

```text
https://github.com/OWNER/REPO/releases/latest/download/MizTrace-Windows-x64-Setup.exe
https://github.com/OWNER/REPO/releases/latest/download/MizTrace-macOS-arm64.dmg
https://github.com/OWNER/REPO/releases/latest/download/MizTrace-macOS-x64.dmg
```

这些链接只有在正式 Release 成功上传对应附件后才能下载；仅上传源码不会自动出现安装包。

## 当前实现与后续分发工作

桌面窗口禁用 Node integration，启用 context isolation 和 sandbox。核心服务运行在独立 Node 子进程，仍只监听回环地址，沿用 token、Host 和 Origin 检查。打包脚本探测 SQLite 能力，并带上 Node 分发许可证。退出 App 时关闭本地服务；未保存的编辑会触发关闭确认。既有 `miztrace` / 旧版 `daytrace` 本地数据目录继续复用。

未提供证书时，macOS 仅允许本地开发或手动工作流生成未签名预览包；推送版本标签正式发行时必须配置 Developer ID Application 证书和 Apple 公证凭据，否则构建直接失败。Windows 可能出现 SmartScreen 提示。macOS 未签名预览版可以查看发布信息，但不能安装自动更新，也不能保证通过系统的首次打开检查。托盘和后台定时采集尚未实现。

## 应用内更新与首次迁移

0.4.0 起，安装版在启动 8 秒后检查 `MIZHOUCL/MizTrace` 的最新正式 GitHub Release；首次安装等待 20 秒。0.5.2 起，手动入口位于桌面菜单栏「更新 → 检查更新…」，紧邻「编辑、视图、窗口」，不再占据页面工具栏。自动检查可关闭，偏好保存在桌面 profile 的 `updates.json`。`managedDevice: true` 禁止检查和下载。检查只读取发布元数据，不发送日记、目录或模型凭据。

检查版本与下载分开：先展示版本、GitHub 发布日期、Markdown 更新说明、包大小。点击「下载更新」才调用 Electron 原生更新器；Windows 通过 Squirrel 下载 `RELEASES` 引用的完整 nupkg，Mac 通过对应架构的 JSON feed 下载 ZIP。下载采用原生更新器，不展示虚构的百分比。下载完成后更新会在下次启动生效，也可点「重启并更新」；立即重启前会阻止尚未保存的日记、手记、模块补充说明及正在进行的保存和 AI 操作。

原来的 0.3 系列安装版没有更新器，无法凭空获取这个能力。第一次需退出旧版并覆盖安装本地 `0.4.0` Setup（Mac 使用签名版应用）；复用原数据目录，不需重新导出日记。以后发布较高的正式版本即可走应用内更新，无需用户手动找安装包。当前实现尚未完成真实 GitHub 发布后的跨版本升级验证。

Windows 每次 Release 必须同时包含 `MizTrace-Windows-x64-Setup.exe`、`MizTrace-版本号-full.nupkg`、`RELEASES`；不要重命名 nupkg。打包脚本校验 RELEASES 中的 SHA-1 与长度，同时提供独立 SHA-256 校验文件。Mac 每个架构同时发布 `.dmg`、`.zip` 和 `update-darwin-架构.json`。不能只上传用户下载用的 Setup 或 DMG。变更仓库地址时同步修改 `desktop/updater.cjs` 中的仓库常量。

## 免费在自己的 Mac 上使用

自己运行 MizTrace 不需要 Apple Developer Program。有以下免费方式：

- **直接运行源码界面**：安装符合项目要求的 Node（建议 Node 24），在项目根目录运行 `node bin/miztrace.js ui`，通过浏览器使用本地界面。
- **本机开发桌面版**：在 Mac 上运行 `npm run desktop:install` 和 `npm run desktop:dev`。这不需要 Developer ID 或 Apple 公证。
- **使用自己信任的已有 App**：将 App 从 DMG 拖入 Applications，退出应用后按下面的临时签名步骤处理。临时签名不需要 Apple 账号或付费证书。

临时签名只修复本机应用的签名完整性，不会获得 Apple 的开发者身份或公证。分享给其他 Mac 用户时，对方也需要自行允许打开；本项目的应用内自动安装更新仍要求 Developer ID 签名。当前工作流允许手动生成未签名测试包，正式版本标签发行仍要求 Developer ID 和公证。

## macOS 签名配置（面向公开分发）

### 首次接入：先申请账号，再取得证书

要让其他用户从 GitHub 下载后正常打开，需要 **Developer ID Application 签名 + Apple 公证 + 随 App 附带公证票据**。仓库里的签名配置只是调用这些服务的代码，不包含 Apple 颁发的身份和证书。免费 Apple 账号或本机临时签名不能提供这种分发体验。

Apple Developer Program 的官方年费为 99 美元，或注册地区的当地币种价格，以付款页面为准。个人开发者可以按个人身份申请；本项目通过 GitHub 分发，不需要上架 Mac App Store。正常首次打开仍可能显示“从互联网下载的 App，是否打开”的系统确认；目标是通过 Gatekeeper，不是去掉所有系统提示。

1. 前往 [Apple Developer Program 注册入口](https://developer.apple.com/programs/enroll/)，使用开启双重认证的 Apple 账号完成注册、身份验证和付款，等待会员资格生效。
2. 在你的 Mac 上打开“钥匙串访问”，选择菜单 **钥匙串访问 → 证书助理 → 从证书颁发机构请求证书**。填写邮箱和名称，CA 邮箱留空，选择“存储到磁盘”，生成 `.certSigningRequest` 文件。后续导出证书要使用这台 Mac 上生成的配套私钥。
3. 登录 [Apple 开发者证书页面](https://developer.apple.com/account/resources/certificates/list)，点击 `+`，选择 **Developer ID Application**，上传上一步的请求文件，下载 `.cer`，双击导入钥匙串。本项目需要的是应用分发证书；不要选择 Apple Development、Apple Distribution 或 Developer ID Installer。
4. 在钥匙串“我的证书”中找到 `Developer ID Application: 你的姓名或组织 (团队ID)`，展开后应有配套私钥。将证书连同私钥导出为 `MizTrace-Developer-ID.p12`，设置并保存导出密码。只有 `.cer`、没有私钥，不能供 GitHub 构建机签名。
5. 在 Mac 终端运行下列命令，复制输出中引号内完整的 `Developer ID Application: ...`，作为 `APPLE_SIGNING_IDENTITY`：

   ```bash
   security find-identity -v -p codesigning
   ```

6. 在开发者账号的 **Membership details** 找到 10 位 `Team ID`，作为 `APPLE_TEAM_ID`。在 [Apple 账号页面](https://account.apple.com/)的“登录与安全 → App 专用密码”生成一个供 MizTrace 公证使用的密码，作为 `APPLE_APP_SPECIFIC_PASSWORD`；`APPLE_ID` 填该开发者账号的登录邮箱。这里使用专用密码，不是 Apple 账号的登录密码。
7. 将导出的 `.p12` 编码成 Base64 并复制到剪贴板。在 Mac 终端执行下列命令，按实际文件位置修改路径：

   ```bash
   base64 -i "$HOME/Downloads/MizTrace-Developer-ID.p12" | tr -d '\n' | pbcopy
   ```

### 配置 GitHub 并验证首次发行

进入仓库 **Settings → Secrets and variables → Actions → New repository secret**，配置以下 6 项。工作流会导入临时 keychain，由 Forge 签名、提交公证并附加票据，构建结束清理证书。不要把证书或密码提交进仓库。

| Secret | 内容 |
| --- | --- |
| `MAC_CERT_P12` | Developer ID Application 证书 p12 的 Base64 |
| `MAC_CERT_PASSWORD` | p12 密码 |
| `APPLE_SIGNING_IDENTITY` | 完整 identity，例如 `Developer ID Application: Your Name (ABCDEFGHIJ)`，不含外层引号 |
| `APPLE_ID` | 已加入开发者计划的 Apple 账号登录邮箱 |
| `APPLE_APP_SPECIFIC_PASSWORD` | 上一步生成的 App 专用密码 |
| `APPLE_TEAM_ID` | 同一开发者团队的 10 位 Team ID，例如 `ABCDEFGHIJ` |

正式标签构建设置 `MIZTRACE_REQUIRE_MAC_SIGNING=1`，拒绝缺失或不完整的签名、公证配置。手动运行工作流仍可生成仅供开发测试的未签名预览包；这些包不会自动发布到 Release。

配置完后，先在 **Actions → Desktop release → Run workflow** 选择包含这些配置的分支。已配置签名的手动构建和正式标签构建都会执行 `Verify macOS distribution signature and notarization`：检查 App 的完整签名、Developer ID 身份、随包公证票据以及 Gatekeeper 执行评估。两种 Mac 架构都应通过，再按上面的发布步骤使用新版本号发行。没有凭据的未签名预览会跳过这项检查，不能当作正式发行验收。

本地构建后可运行 `node scripts/verify-macos-release.mjs` 执行相同检查。任何检查失败都阻止正式发布。`desktop-smoke.mjs` 直接启动可执行文件，只能验证程序功能，不能代替下载后的系统安全检查。

正式发行后，分别用 Apple Silicon 和 Intel Mac 的浏览器下载对应 DMG，将 App 拖到 Applications 并从 Finder 首次打开，确认能启动和保存日记。应使用此前未对该应用解除系统限制的测试环境，保留下载产生的 quarantine 标记。源码改好、添加 Secrets 或 CI 通过都不会修复已经公开的旧安装包，用户需要下载新发布的签名版本。

签名启用 hardened runtime 和 Node/Electron 所需的 JIT 权限。首次签名发布需要在两种 Mac 架构上实际验证内置 Node、SQLite、Gatekeeper 首次启动和两个签名版本之间的升级。本机 Windows 构建不能代替这些验证。

## 已下载版本提示“已损坏，无法打开”

2026-11-27 在 macOS arm64 上检查 0.5.2 安装包时，应用仍携带 Electron 的临时签名，`codesign --verify --deep --strict` 报 `code has no resources but signature indicates they must be present`，没有 Developer ID 和完整资源签名。浏览器下载附带的 quarantine 标记触发了系统检查，因此出现“已损坏”弹窗。仅有 DMG 下载链接和构建冒烟测试通过不能证明可正常安装。

如果只是自己使用，不需要购买证书：确认应用来自自己的可信构建，将 App 拖入 Applications 并退出后，可以对**自己电脑上的这个应用**做临时修复：

```bash
codesign --force --deep --sign - --preserve-metadata=entitlements "/Applications/MizTrace.app"
codesign --verify --deep --strict "/Applications/MizTrace.app"
xattr -dr com.apple.quarantine "/Applications/MizTrace.app"
```

上述本机修复不修改日记，也不关闭全局 Gatekeeper，但不提供开发者身份、公证或应用内更新能力；不能把修复后的包作为已签名正式版分发。重新下载旧安装包或覆盖安装会带回旧问题。正式修复必须配置上面的 Secrets，用新的版本号发布，不能只修改源码后重跑旧标签。
